# 长期记忆与续写检索

在任何跨章续写、隔日恢复、跨会话继续、旧线索回收或全书改稿任务中读取本文件。长期记忆是项目内的持久文件，不是模型对旧对话的印象。

## 四层记忆

1. **稳定正典**：`story-bible/`、已确认大纲和 `memory/decisions.md`。记录不应被普通续写随意改变的事实与作者裁决。
2. **全局压缩记忆**：`memory/book-summary.md`。记录当前故事阶段、跨卷人物关系、长期目标、已揭示真相和仍有效的核心约束。
3. **章节检索记忆**：`manuscript/index.md` 与 `memory/chapters/NNNN.md`。前者用于定位，后者用于快速判断哪些旧章需要回读。
4. **当前运行状态**：`continuity/state.json`、`timeline.md` 和 `threads.md`。记录下一章写作直接依赖的位置、知识、物品、伤势、关系和活跃线索。

压缩记忆只负责检索和恢复上下文。与正文冲突时，以用户裁决、稳定正典和已提交原文为准，并修复错误的记忆文件。

## SQLite 派生检索层

`.novel-cache/novel-memory.sqlite3` 是从上述 Markdown、JSON、章节正文和索引生成的本地派生缓存，不是第五层正典。它索引文档分块，并从结构化状态、稳定标签和账本中提取人物、地点、物品、关系、线索、时间与章节实体。

```powershell
python -X utf8 .\scripts\novel_memory.py status "<project-root>"
python -X utf8 .\scripts\novel_memory.py rebuild "<project-root>"
python -X utf8 .\scripts\novel_memory.py update "<project-root>"
python -X utf8 .\scripts\novel_memory.py search "<project-root>" "林某D" --entity-type character --require-fresh
python -X utf8 .\scripts\novel_memory.py search "<project-root>" "T-003" --entity-type thread --require-fresh
python -X utf8 .\scripts\novel_memory.py search "<project-root>" "旧邮局 铜钥匙" --mode all --require-fresh
```

数据库缺失、损坏、版本不兼容或过期时，从项目文件重建；不得从数据库导出内容覆盖正文或账本。`search` 返回路径、标题、行号和短摘录，用于决定回读哪些原文，不替代回读。没有数据库时继续使用 `rg` 的文件检索协议，不阻塞项目恢复。

实体抽取优先使用 `continuity/state.json`、时间线、线索账本、章号和明确标签，例如 `人物：林某D`、`地点：旧邮局`、`物品：铜钥匙`、`关系：林某D-周槐`、`线索：T-003`。没有结构化证据时不通过猜测生成实体。

## 续写前强制检索

每次续写按以下顺序执行：

1. 读取 `novel.json`，确认当前已提交章号和项目状态。
2. 读取 `memory/book-summary.md`、`memory/decisions.md`、`manuscript/index.md`、`continuity/state.json` 和活跃线索。
3. 读取最近 2-3 章的记忆卡，恢复短期因果、语气和场景余波。
4. 从本章合同提取人物、地点、物品、关系、设定规则和线索 ID。
5. 先检查 SQLite 新鲜度；新鲜时按实体类型与关键词检索，缺失或过期时使用 `rg` 在 `memory/chapters/`、`manuscript/index.md`、`continuity/` 和 `story-bible/` 中搜索这些关键词与稳定 ID。
6. 对每个重要命中回读对应章节原文，不把记忆卡当作原文替代品。至少回读上一章结尾，以及所有会在本章兑现、反转或再次出现的旧线索原文。
7. 形成内部“续写上下文包”：已确认事实、当前人物状态、知识边界、关系余波、活跃线索、必须回调的原文锚点、禁止矛盾和本章允许变化。

找不到前文文件时，不得声称拥有长期记忆。先搜索项目；仍缺失时说明只能基于当前材料续写，并请求提供缺失章节或允许重建索引。

## 章节记忆卡

每个已提交章节必须有 `memory/chapters/NNNN.md`，使用稳定结构：

```markdown
# 第0001章记忆卡：雾港来信

- 正文：[0001-雾港来信](../../manuscript/chapters/<chapter-file>)
- 状态：committed
- POV：林某D
- 故事时间：第一日凌晨
- 地点：旧邮局

## 事实摘要

只写正文明确发生的事实和直接后果。

## 状态变化

- 人物：
- 关系：
- 知识与误信：
- 物品与资源：

## 线索与回调

- 新增：T-001
- 推进：
- 回收：
- 原文锚点：用于未来回读的短语或场景位置，不大量复制正文。

## 续写约束

- 下一章必须承接：
- 不能违反：
```

记忆卡不能写入大纲中尚未发生的计划，也不能把人物猜测改写成客观事实。角色“知道”“相信”“读者知道”要分别记录。

## 全书压缩记忆

`memory/book-summary.md` 保持短而稳定，按卷、阶段性转折或重大正典变化更新，不要把每章摘要再次复制进去。建议包含：

- 故事承诺与核心冲突
- 当前阶段和最近不可逆转折
- 主要人物当前长期目标、关系与未愈合后果
- 已确认世界规则和重要例外
- 已揭示真相与仍在运作的误导
- 跨卷活跃主线与预计回收范围

当文件变长时按“仍影响未来写作”压缩；已完结且不再产生影响的局部事件保留在章节记忆卡和时间线中。

## 作者决策与追溯修改

`memory/decisions.md` 记录用户明确作出的创作裁决和追溯修改，包括决策 ID、生效章节、被替代事实、需要同步的章节或账本。普通写作推断不得进入该文件。

发生追溯修改时：先记录决策，再更新故事圣经和受影响正文，然后重建相关章节记忆卡、索引摘要、时间线、线索状态和全书压缩记忆。未完成级联同步前标记项目为 `revision`，不要继续写新章。

## 写后原子提交

一章的持久化顺序固定为：

```text
章节正文
  -> 连续性检查
  -> 章节记忆卡
  -> 章节索引
  -> 当前状态、时间线与线索账本
  -> 必要时更新全书压缩记忆
  -> 最后推进 novel.json
```

验证器发现正文没有索引条目、索引链接失效或缺少同章记忆卡时，该章视为未完整提交。修复文件之间的对应关系后才能继续下一章。

正式章节使用 [controlled-automation.md](controlled-automation.md) 的暂存包和事务提交。提交成功后如果 SQLite 已存在，脚本执行增量更新；缓存更新失败时章节仍以文件为准，并明确要求运行 `rebuild`，不得把缓存失败伪装成正文提交失败或用旧缓存继续宣称一致。

## 长篇检索原则

- 最近章节提供局部连续性，旧章检索提供长期因果；两者都要有。
- 人名之外也搜索旧称、化名、地点别名、物品 ID 和线索 ID。
- 同一角色跨阶段声音变化要由人物弧解释，不能简单复制第一章口吻。
- 引用记忆卡后仍需回读关键原文，尤其是承诺、预言、证词、规则首次说明和关系转折。
- 不为了节省上下文删除重要约束；应缩短摘要并保留原文链接。
