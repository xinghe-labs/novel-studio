# 互动建书

当用户希望通过问答从灵感、零散设定或旧构思逐步确定长篇小说或完整短故事框架，并在确认后开始正文时读取本文件。同时读取 [planning.md](planning.md)；作品类型为 `short_story` 时再读取 [short-story-mode.md](short-story-mode.md)，需要跨会话落盘或即将开始写作时再读取 [project-contract.md](project-contract.md)。

## 目标与边界

互动的目的不是填满一张固定问卷，而是用最少轮次解决会改变故事方向的分歧。复用用户已经给出的信息，跳过已经明确的阶段。书名、精确章数、次要人物和暂时用不到的设定通常可以后定；但新短故事必须在正式项目创建前确认最终标题、完整场景图、高潮和结尾，因为标题参与稳定项目 ID 的语义 slug 选择。

- 每轮集中处理 1 个决策主题，通常只提出 2-4 个相互关联的问题。
- 用户不确定时给出 2-3 个差异实质明确的方向，说明它们对冲突、代价、篇幅、人物弧或结局的影响；不要只换措辞制造假选项。
- 允许用户选择、混合、修改或自行提出方案。推荐项必须说明依据来自用户的哪些偏好。
- 区分“用户已确认”“当前暂定”“仍未决定”和“已排除”。模型推断只能进入暂定区。
- 不因小细节阻塞推进，也不在核心冲突、人物驱动力、世界硬规则或叙事声音尚未成立时大量生成正文。

## 两级 95% 理解闸门

“95%”是面向执行准备度的透明估计，不是统计概率。每轮先展示“已理解”“仍不确定”“当前理解信心”，然后只追问会改变最终方案的问题。只在所有阻断项已由用户确认或明确委托、剩余未知均可逆且不会改变目标时，才报告 95% 或更高。

1. **需求层闸门**：用于新建 Skill 工作流、市场研究目标、重大改稿或从零建书。至少覆盖目标与交付、受众和平台、范围与篇幅、资料来源、商业与原创优先级、内容边界、决策权限和确认方式。
2. **故事层闸门**：用于具体作品。至少覆盖读者承诺、主角驱动力、对抗力量与失败代价、人物关系、世界硬规则和叙事声音；长篇还要明确全书方向和第一阶段写作合同，短故事还要明确全篇升级、高潮选择与结尾兑现。

存在任一会实质改变结果的未决项时，信心最多报告 94%。用户说“由你决定”表示授权分析，不表示自动确认正典：先给候选、依据和推荐，用户确认后才把该项记为已确认。用户已确认的项目文件可以直接满足对应项，不要为了形式重新提问。

两级闸门不应用于阻塞简单、确定的操作，例如查询项目状态、修复索引链接或在完整章节合同下继续一章；这些任务读取项目文件即可恢复充分上下文。新书、重大方向变化、市场选型和会改变正典的模糊请求必须执行闸门。

## 会话发现与恢复

已有项目先查找 `planning/framework-session.md`，再读取 `memory/decisions.md`、已确认的故事圣经和总纲。尚未建项目的新短故事改为读取 `<work-root>/research/short-story-session.md`、已有市场研究和候选审批状态：

1. 从“下一轮”恢复，不重新询问已确认事项。
2. 用户本轮修改旧决定时，把旧决定移入“已排除或被替代”，并记录替代关系。
3. 项目已经建立时，每轮出现实质决定后都更新项目会话文件的正文、`stage` 和 `updated_at`；不要等到聊天结束才写回。
4. 新短故事在项目尚未建立时，每轮实质决定都更新工作目录会话文件。即使已有暂定标题、已选原创方向或需要跨上下文继续，也不能提前初始化项目。
5. 长篇仍沿用原有行为：用户确定专用项目目录和暂定书名后可以初始化项目并继续在项目会话文件中策划。
6. 两种会话文件都是策划过程记录，不是正典。只有用户确认并同步到 `story-bible/`、`outlines/` 和 `memory/decisions.md` 的内容才成为正典。

会话文件的 frontmatter 使用以下状态：

```yaml
---
schema_version: 1
stage: discovery
confirmation: pending
requirements_confidence: 0
story_confidence: 0
updated_at: 2026-01-01T00:00:00+00:00
---
```

`stage` 只能是 `discovery`、`direction`、`core`、`characters`、`world`、`voice`、`outline`、`confirmation` 或 `complete`。框架未确认时 `confirmation` 为 `pending`；确认完成后必须同时设置 `stage: complete` 与 `confirmation: confirmed`。两个信心字段使用 0-100 的整数；确认完成时二者都不得低于 95。

## 自适应阶段

以下阶段是覆盖检查，不是必须逐项机械执行的九轮问答。一个回答可以解决多个阶段，信息齐全时直接进入确认。

1. **素材发现 `discovery`**：提取原始灵感、必须保留、明确避免、目标读者和大致规模。
2. **方向选择 `direction`**：当故事方向未定时提出 2-3 个可持续方向，比较读者承诺、主要代价和核心压力。
3. **故事核心 `core`**：确定主角欲望、对抗力量、失败代价、内在错误信念和主题问题。
4. **人物系统 `characters`**：确定关键人物的利益、情感、权力关系、知识边界和会在压力下暴露的缺陷。
5. **世界规则 `world`**：只确定影响选择和因果的规则、成本、控制者、例外及违规后果。
6. **叙事声音 `voice`**：确定 POV、叙述距离、时态、气质、节奏、内容边界和角色声音。
7. **大纲 `outline`**：形成与作品类型匹配的因果骨架。长篇可先确认全书方向、第一卷和前 3-5 章，不伪装已经规划了尚未决定的远期细节；短故事必须确认能覆盖完整正文的场景图、高潮选择和结尾落点。
8. **框架确认 `confirmation`**：展示完整确认单，清楚分开已确认、暂定和未决定事项。
9. **完成 `complete`**：同步正典。长篇切换到第一章合同与分章流程；新短故事先按确认结果创建并绑定稳定项目，再切换到全篇合同、场景推进与唯一正文流程。

## 每轮交互

先用一小段话复述当前理解，再展示本轮新增或变化的决定，然后提出下一组问题。选项应包含直接后果，例如：

```markdown
### 本轮要决定：故事的主要压力

A. 身份暴露
- 读者承诺：秘密逐层逼近公开
- 长期压力：主角每次使用能力都会留下证据
- 更适合：悬疑、追逃、道德困境

B. 记忆争夺
- 读者承诺：不断重构人物关系与真相
- 长期压力：重要人物对同一过去拥有冲突版本
- 更适合：群像、关系拉扯、心理悬疑

请选 A、B，或说明想混合的部分。
```

不要连续提出与当前分歧无关的问题。用户回答后，先吸收答案和处理冲突，再进入下一轮。

## 会话文件写回

项目内 `planning/framework-session.md` 和新短故事建项前的 `<work-root>/research/short-story-session.md` 至少维护以下区域：

- **用户原始材料**：保留用户输入的事实性摘要，不替用户润色成新设定。
- **理解状态**：分别记录需求层和故事层已经确认、已委托及仍阻断的事项，支撑信心判断。
- **已确认**：带稳定 ID 的作者裁决及其影响范围。
- **暂定**：可继续调整的工作假设，并标明为什么暂定。
- **未决定**：真正影响后续的开放问题，不堆积无关细节。
- **已排除或被替代**：避免后续再次推荐已经否决的方向。
- **下一轮**：下一次恢复时优先处理的 1 个主题和至多 4 个问题。
- **框架确认单**：在确认阶段生成的完整可读版本。

如果用户只是在聊天内构思一次性片段且不要求落盘，可以不创建会话文件；跨章节长篇、连载，以及任何已经触发完整短故事分支的工作都必须落盘。新短故事会话还要记录最近 3-6 个月研究窗口、候选审批状态、原创方向选择、最终标题与建项状态；未经确认时 `project_id` 保持空值。

## 确认闸门

确认单至少覆盖：书名、作品类型、题材与读者、预计规模、一句话故事、读者承诺、核心冲突、失败代价、主题问题、主角驱动力、主要对抗力量、关键人物关系、世界硬规则、叙事声音、必须保留、明确避免和仍未决定事项。长篇书名可以暂定，并补充全书阶段与第一阶段合同；新短故事必须使用最终确认标题，并补充参考候选审批、原创方向选择、全篇场景图、高潮选择、结尾类型与兑现方式、内容尺度和交付目标。

只有需求层和故事层信心均达到 95%，且用户明确表示“确认”“按这个写”“开始写”或同等含义，才执行确认提交：

1. 新短故事先复核参考候选为 `approved`、深度分析基于获批候选、原创方向已由作者选择、完整确认单没有阻断项。Agent 从最终标题选择 1-3 个英文小写语义词，使用 `project-create --work-type short_story --short-story-slug <slug>` 创建项目，再把原工作绑定到脚本实际返回的项目 ID。不要在确认之前预留空项目。
2. 已有项目或刚绑定的新项目取得单写者租约并执行 `write-check`。新短故事把工作目录中获批的来源记录、市场扫描、参考机制、原创性计划和会话记录同步到项目合同对应路径；未获批材料继续留在工作目录。
3. 把确认内容分别写入 `story-bible/premise.md`、`cast.md`、`world.md`、`style-guide.md` 和 `outlines/master-outline.md`。
4. 在 `memory/decisions.md` 记录本次框架确认、适用范围、市场方向选择和同步文件。
5. 更新 `memory/book-summary.md` 的稳定故事承诺与起始正典。
6. 清除已经解决的“下一轮”问题，再按 [controlled-automation.md](controlled-automation.md) 使用 `framework-state` 将项目会话 frontmatter 更新为 `stage: complete`、`confirmation: confirmed`；状态命令不能替代正典同步。
7. 更新 `novel.json` 的 `status`、POV、时态、目标篇幅和 `updated_at`；没有确认的字段保持空值或 `null`。运行项目与长期记忆验证，刷新工作基准并释放租约。
8. 建立当前写作单位合同。长篇建立第一章合同；短故事建立全篇合同和首个场景合同。用户已经要求“开始写”时，在同一任务继续读取 [drafting.md](drafting.md)、[long-term-memory.md](long-term-memory.md) 和 [continuity.md](continuity.md)，进入对应正文流程，不再重复请求总框架确认。

新短故事项目创建成功但绑定、同步或验证失败时停止，报告项目 ID、工作 ID 和失败步骤；不生成正文，不自动删除项目，也不换一个工作上下文绕过失败。

用户只是说“先看看框架”时停在确认单，不创建正文。用户要求探索式写作时，可以在确认前写明确标记为试写、且不进入章节索引的样章；样章不能自动成为已提交第一章。

## 完成检查

- 用户能清楚看出哪些是自己的决定，哪些仍是模型建议。
- 信心达到 95% 的依据可由会话文件中的已确认、已委托和阻断项复核，不用没有依据的百分比装饰回答。
- 核心节点能用“因为、所以、但是”形成因果，而不只是事件排列。
- 关键人物有独立驱动力，世界规则有成本和可观察后果。
- 确认单与故事圣经、总纲、作者决策和会话状态一致。
- 确认后当前写作单位有明确的进入状态、目标、阻力、关键变化和结束状态；短故事还明确高潮选择与结尾兑现。
- 跨会话恢复不会重复已确认问题，也不会把已排除方案重新包装后提出。
